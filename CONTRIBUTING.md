# Contributing

How to propose a change. Setup is in the [getting started guide](docs/getting-started.md); how the pieces fit is in the [architecture overview](docs/architecture.md).

## 1. Workflow

1. Pick a story from [docs/stories/](docs/stories/) (each milestone has an index; current status is in [docs/progress/](docs/progress/README.md)).
2. Create a branch from `main`.
3. Make the change with tests, then run the local checks (section 5).
4. Open a pull request into `main` and wait for the checks to pass.

## 2. Branch names

| Kind | Pattern | Example |
|---|---|---|
| Story work | `feat/<story-id>-<slug>` | `feat/e2-s2-custodian-export` |
| Documentation only | `docs/<topic>` | `docs/roadmap-wording` |
| Bug fix | `fix/<slug>` | `fix/date-parsing` |

Use the story id (for example `E2-S2`) in commit messages and the pull request too.

## 3. Commit messages

A short imperative subject (for example `Add custodian export (E2-S2)`), a body when the why is not obvious, and one logical change per commit.

## 4. Pull requests

Use the template that appears when you open one. It asks for a summary, the story, a checklist, **E2E Local Testing Evidence** and how you tested. The evidence is real commands, requests, logs or screenshots from running the change locally, mapped to the story's acceptance criteria; unit test output does not count. The exact rules are in [CLAUDE.md](CLAUDE.md).

Progress is tracked in `docs/progress/`. When you start, finish, block or drop a story, update the progress files in the same pull request (the rules are in [CLAUDE.md](CLAUDE.md)). A test checks the tables stay consistent.

Repository settings such as required checks are in [docs/repo-settings.md](docs/repo-settings.md).

## 5. Local checks

```bash
uv run ruff check .
uv run ruff format --check .
uv run mypy
uv run pytest
```

`uv run pytest -m "not slow"` is the quick loop. See [docs/testing.md](docs/testing.md) for what the tests and guards cover and the coverage threshold.

## 6. Rules of the road

- **Determinism.** The same configuration must produce byte-identical output. Use named random streams (`derive_rng(seed, "label", ...)` in `rng.py`), never the global `random`, the clock, `hash()`, or unordered iteration (sort sets and dictionaries before writing).
- **Money is `Decimal`.** A `float` for money is a bug.
- **Synthetic data only.** Never paste real client, firm or personal data anywhere in the repository. Guard tests check emails, phone numbers, tax ids and tracked files.
- **Generated output changes need a version bump.** If any generated byte changes on purpose, bump `GENERATOR_VERSION`, add an entry at the top of [docs/datagen-changelog.md](docs/datagen-changelog.md), and refresh the recorded checksums (`python scripts/update_expected_checksums.py`).
- **Concept first.** A new column needs a concept in `sources/concepts.yaml` before it appears in a source profile.
- **Truth never leaks.** Code that builds or writes `exports/` must not import `answer_keys`, and no truth identifier may appear in an export. `onboardkit-gen check` and a test enforce both.
- **Generated data is not committed.** `data/generated/` is git-ignored.

## 7. How to add a mess type

Mess types are small classes in `src/onboardkit/datagen/mess/`; `names.py` and `formats.py` are good models, and `noop.py` shows the minimal shape.

1. Create `mess/<name>.py` with a class that has `name`, `description`, `touches` (concept ids it may change), `structural` (True only if it adds or removes rows), `max_rate`, a `subtypes` set, and `apply(ctx, data)`. Draw randomness only from `ctx.rng(source)`.
2. Make `apply` return one `MessEvent` for every change, created with `ctx.event(...)`, carrying before and after values, the effect, and (where it applies) severity and ambiguity.
3. Register it with `@register` and import the module in `mess/__init__.py`.
4. Add the name to `MESS_TYPE_NAMES` in `config.py` and to `CANONICAL_ORDER` in `mess/registry.py` (the order is part of the dataset definition).
5. Give it an intensity in each preset under `src/onboardkit/datagen/presets/`.
6. Add tests next to the existing ones in `tests/datagen/mess/`: what it changes, that it leaves untouched rows alone (see `test_mess_isolation.py`), and that every subtype appears at the `nightmare` preset (`test_mess_coverage.py` checks this for all types).
7. Regenerate the catalogue: `python scripts/mess_catalogue.py` (a test fails if `docs/mess-catalogue.md` is stale).
8. Bump the generator version, update the changelog and checksums (section 6), and add a glossary entry if you introduced a new term.

## 8. How to add a source column

1. Add the concept to `sources/concepts.yaml` (id, description, value type). Ids are stable because answer keys depend on them.
2. Add a `ColumnSpec` to the source's profile (`sources/custodian.py`, `crm.py` or `book_of_business.py`) with the header and a formatter from `sources/formatters.py`.
3. Add the value to the source's projection from the truth firm, in the same file.
4. The answer keys pick the column up from the profile and rows automatically; run `onboardkit-gen check` on a generated dataset to confirm.
5. Add a glossary entry if the column introduces a new term, and update [docs/source-systems.md](docs/source-systems.md).
6. Add or update tests under `tests/datagen/sources/`.
7. Bump the generator version and refresh the checksums (section 6).

## 9. Documentation

Documents live in `docs/`, with the roadmap, epics and stories described in [CLAUDE.md](CLAUDE.md). Planning documents describe capabilities and outcomes; technical detail belongs in story files. Tests check that relative links resolve, that commands in code blocks are valid, and that quoted examples in the demo walkthrough still exist. When you move or rename a document, fix every link to it.
